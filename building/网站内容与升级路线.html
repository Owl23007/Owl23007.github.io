网站内容与升级路线 ​

这篇记录用于统一管理博客接下来的内容补全、功能升级和视觉优化。原则是先保证内容结构清晰，再补齐体验能力，最后做持续性的工程优化。

一、还没完成的文章内容 ​

1. 优先补齐的系列 ​

Go 系列 当前已经有入门、基本语法、数据结构、面向对象和 Gin 文章，但索引里的路线还有大量未完成项。

前端系列 目录中还有很多计划项没有对应文章。

操作系统系列 已有进程、存储、文件、I/O 等主题，但部分文章缺少 frontmatter。

Android 系列 目前只有索引与基本的 Android 组件介绍。

UE5 系列 目前只有索引。

2. 需要整理的旧文章 ​

这些文章更适合做“质量整理”，不是新增大内容：

  • 我的第一篇博客：作为历史记录保留即可，可以加一个开头说明“早期建站记录”。
  • GitHub食用指南：标题和术语可以统一空格，例如 GitHub 食用指南。
  • Nova HTTP框架的设计、开发与测试：内容比较完整，可以作为近期重点文章，继续补充 benchmark 结论和项目链接。
  • Electron 踩坑记：适合归入“开发日志”标签，和建站日志区分开。

二、网站开发升级顺序 ​

第一阶段：内容结构稳定 ​

目标是让读者能快速判断“这里有什么、该从哪里看”。

  1. 统一文章 frontmatter
  2. 修正 README 中脚本说明，例如 preview 和 serve 不一致的问题
  3. 为 building 增加侧边栏，posts 暂时保留时间线
  4. 暂不单独拆 life 板块，先使用 tags 区分生活内容

第二阶段：阅读体验增强 ​

目标是让已有内容更好读。

  1. 优化 Timeline 的时间线样式
  2. 首页减少装饰感，突出最新文章和系列入口
  3. 统一文章卡片、系列卡片、状态卡片的圆角、边框和阴影
  4. 移动端检查标题、标签、按钮是否换行稳定

第三阶段：互动能力 ​

目标是让文章能承接反馈。

  1. 基于 GitHub Discussions 接入 giscus
  2. 只在文章页开启评论，首页、索引页、组件文档页不开启
  3. 评论组件配置放在主题配置里，不写死在组件内部
  4. 给 publish: false 或特殊页面提供关闭评论的 frontmatter

第四阶段：工程质量 ​

目标是降低后续维护成本。

  1. 补充 pnpm run type-check
  2. 补充 pnpm run build
  3. 清理已生成的 .vitepress/.temp、.vitepress/dist 对仓库状态的影响
  4. 梳理 CI/CD 文档和实际 workflow 是否一致

三、布局美化方向 ​

首页 ​

  • Hero 区保持首屏信号清晰：头像、站点标语、主要入口。
  • 最新文章和系列专栏作为首页主体，减少纯装饰元素。
  • 统计卡片保持轻量，避免和文章卡片抢视觉优先级。

文章列表 ​

  • posts 继续使用时间线，适合按时间浏览。
  • series 使用卡片入口和侧边栏，适合体系化学习。
  • building 使用时间线加侧边栏，适合记录迭代过程。

评论区 ​

  • 评论区应放在正文之后、上一篇/下一篇导航之前或之后都可以。
  • 视觉上保持轻量，不要让评论组件成为文章主体。

四、近期执行清单 ​

  • 建立内容与升级路线文档
  • 统一缺失 frontmatter 的系列文章
  • 优化 Timeline 样式
  • 为 building 配置侧边栏
  • 接入 giscus 评论
  • 检查 README 与 package scripts 是否一致
